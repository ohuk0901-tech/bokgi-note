# 복기노트 이벤트 정의서

작성일: 2026-07-19

이 문서는 복기노트에서 어떤 사용자 행동을 이벤트로 기록할지, 왜 그 이벤트가 필요한지, 어떤 기준으로 기록할지 정리한 문서입니다.

목적은 단순히 숫자를 많이 모으는 것이 아닙니다. 나중에 “왜 이 데이터를 수집하기로 했는지”, “이 숫자로 무엇을 판단하려 했는지”, “이 기준이 왜 이렇게 정해졌는지”를 다시 확인하기 위한 운영 기준입니다.

## 1. 이 이벤트를 수집하려는 이유

복기노트의 목표는 사용자가 투자 판단을 기록하고, 시간이 지난 뒤 다시 읽으며, 자신의 판단 패턴과 실수를 발견하고, 결국 자신만의 투자 세계관과 행동 원칙을 다듬게 만드는 것입니다.

그래서 분석도 단순 방문 수보다 아래 질문에 답하는 데 집중합니다.

| 핵심 질문 | 알고 싶은 것 |
| --- | --- |
| 사용자가 매일 투자 일기를 쓰러 오는가 | 가입만 하고 끝나는지, 기록 루틴이 생기는지 |
| 투자 일기를 실제로 작성하는가 | 버튼만 누른 것인지, 템플릿 위에 자기 생각을 남기는지 |
| 1주/3개월/1년 뒤 다시 볼 메모를 여는가 | 시간이 지난 판단을 다시 보는 루틴이 작동하는지 |
| 다시 본 메모를 수정하는가 | 단순 열람이 아니라, 과거 판단에 새 생각을 덧붙이는지 |
| 이번 주 기록을 모아 주간 복기를 하는가 | 주말이나 여유 시간에 한 주를 정리하는 습관이 생기는지 |
| 복기 중 대표 메모를 다시 보고 수정하는가 | 복기가 투자 세계관/행동 원칙 업데이트로 이어지는지 |

## 2. Vercel Analytics만으로 부족한 이유

Vercel Web Analytics는 어떤 페이지에 몇 명이 들어왔는지 보여줍니다.

예를 들어 아래는 알 수 있습니다.

- `/dashboard`에 몇 명이 들어왔는지
- `/login`에서 얼마나 많이 머물렀는지
- `/notes/:id` 화면이 몇 번 열렸는지
- `/reviews/:id` 화면이 몇 번 열렸는지

하지만 아래는 알기 어렵습니다.

- 투자 일기 작성 버튼을 눌렀는지
- 새 투자 일기가 실제로 만들어졌는지
- 템플릿만 열린 상태인지, 사용자가 자기 생각을 썼는지
- 1주/3개월/1년 복기 대상 메모를 열었는지
- 복기 후 메모를 수정했는지
- 대표 메모를 복기 중 다시 보고 고쳤는지

그래서 페이지 방문은 Vercel Analytics로 보고, 핵심 행동은 앱 안에서 별도 이벤트 코드로 기록합니다.

## 3. 이벤트 수집 원칙

1. 메모 본문은 저장하지 않습니다.
2. 메모 제목도 이벤트에는 저장하지 않습니다.
3. 종목명, 금액, 감정 문장, 계좌 정보, API 키 같은 민감정보는 저장하지 않습니다.
4. 사용자의 실제 행동을 판단하는 데 필요한 최소한의 정보만 저장합니다.
5. 자동저장은 여러 번 발생하므로, 의미 있는 작성 이벤트는 조건을 만족했을 때 최초 1회만 기록합니다.
6. “의미 있는 작성” 기준은 모든 작성/수정 이벤트에서 `20자 이상`으로 통일합니다.

## 4. 20자 기준을 쓰는 이유

모든 작성/수정 이벤트의 기준은 `20자 이상`입니다.

단, 여기서 중요한 점은 전체 본문 길이가 20자 이상이라는 뜻이 아닙니다.

복기노트에는 기본 템플릿이 들어갑니다. 투자 일기나 주간 복기 템플릿은 사용자가 아무것도 쓰지 않아도 이미 글자가 많습니다. 그래서 전체 글자 수만 보면 실제로 아무것도 쓰지 않았는데 “작성했다”고 잘못 판단할 수 있습니다.

따라서 기준은 아래처럼 잡습니다.

| 상황 | 기준 |
| --- | --- |
| 새 투자 일기 | 템플릿 대비 사용자가 추가/수정한 글자 수가 20자 이상 |
| 주간 복기 | 템플릿 대비 사용자가 추가/수정한 글자 수가 20자 이상 |
| 1주/3개월/1년 복기 메모 | 복기 화면으로 열었을 때의 본문 대비 변경된 글자 수가 20자 이상 |
| 대표 메모 수정 | 대표 메모를 열었을 때의 본문 대비 변경된 글자 수가 20자 이상 |

20자를 기준으로 정한 이유는 아래와 같습니다.

- 모바일에서도 부담 없이 쓸 수 있는 짧은 한 문장 정도입니다.
- 실수로 줄바꿈을 하거나 글자를 조금 건드린 것을 작성으로 보지 않을 수 있습니다.
- 30자나 50자는 초반 베타 사용자에게 너무 높은 기준일 수 있습니다.
- 모든 이벤트 기준을 하나로 맞추면 나중에 분석할 때 헷갈리지 않습니다.

예시:

- “왜 샀는지 다시 보니 너무 조급했다”는 의미 있는 작성입니다.
- “ㅇ”, “확인”, 줄바꿈 몇 번은 의미 있는 작성으로 보지 않습니다.
- 템플릿 질문만 그대로 있는 상태는 의미 있는 작성으로 보지 않습니다.

## 5. 저장 방식 개념

이벤트 코드를 앱에 넣으면, 사용자가 특정 행동을 했을 때 이벤트 기록이 하나 남습니다.

예를 들어 사용자가 투자 일기를 열고 템플릿 위에 자기 생각을 20자 이상 쓰면 아래 같은 기록이 남습니다.

```json
{
  "event_name": "investment_journal_edited",
  "user_id": "사용자 ID",
  "page_path": "/notes/...",
  "properties": {
    "source": "dashboard",
    "note_kind": "investment_journal",
    "delta_text_length_bucket": "20_99"
  },
  "created_at": "2026-07-19T12:00:00Z"
}
```

이벤트에는 사용자가 쓴 본문이 들어가지 않습니다. 대신 “투자 일기에서 20자 이상 실제 작성이 있었다”는 사실만 남깁니다.

## 6. 공통 속성

모든 이벤트에 공통으로 붙이면 좋은 정보입니다.

| 정보 | 설명 | 예시 |
| --- | --- | --- |
| `event_name` | 이벤트명 | `investment_journal_edited` |
| `user_id` | Supabase 사용자 ID | `auth.users.id` |
| `page_path` | 이벤트가 발생한 화면 | `/dashboard`, `/notes/:id` |
| `source` | 사용자가 어디에서 들어왔는지 | `dashboard`, `folder`, `review_due` |
| `device_type` | 기기 구분 | `mobile`, `desktop`, `tablet` |
| `created_at` | 이벤트 발생 시각 | 서버 기준 시각 |

본문 길이는 정확한 숫자보다 구간으로 저장하는 편이 안전합니다.

| 구간 | 의미 |
| --- | --- |
| `20_99` | 짧은 기록 |
| `100_299` | 어느 정도 생각을 남긴 기록 |
| `300_plus` | 긴 기록 |

저장하지 말아야 할 정보:

- 메모 본문
- 메모 제목
- 종목명
- 투자 금액
- 계좌 정보
- 사용자가 쓴 감정 문장
- 사용자가 작성한 투자 원칙 문장

## 7. 핵심 이벤트 목록

이번 단계에서 우선 수집할 이벤트입니다.

| 우선순위 | 이벤트명 | 한글명 | 이 이벤트로 알고 싶은 것 |
| --- | --- | --- | --- |
| 필수 | `investment_journal_created` | 투자 일기 생성 | 사용자가 오늘 기록을 만들었는지 |
| 필수 | `investment_journal_edited` | 투자 일기 실제 작성 | 템플릿 위에 자기 생각을 20자 이상 남겼는지 |
| 필수 | `due_review_note_opened` | 다시 볼 메모 열기 | 1주/3개월/1년 복기 대상 메모를 실제로 열었는지 |
| 필수 | `due_review_note_edited` | 다시 볼 메모 수정 | 과거 판단을 다시 보고 20자 이상 새 생각을 남겼는지 |
| 필수 | `due_review_completed` | 다시 볼 복기 완료 | 1주/3개월/1년 복기를 완료 처리했는지 |
| 필수 | `weekly_review_opened` | 이번 주 복기 열기 | 이번 주 기록 모아보기 화면에 들어갔는지 |
| 필수 | `weekly_review_edited` | 이번 주 복기 실제 작성 | 주간 복기 템플릿 위에 20자 이상 회고를 남겼는지 |
| 중요 | `pinned_note_opened_from_review` | 복기 중 대표 메모 열기 | 복기 중 대표 메모를 참고했는지 |
| 중요 | `pinned_note_updated_from_review` | 복기 중 대표 메모 수정 | 복기 후 대표 메모를 20자 이상 고쳤는지 |

## 8. 이벤트 상세 정의

### 8.1 투자 일기 생성

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 오늘 투자 일기를 만들었는가 |
| 이벤트명 | `investment_journal_created` |
| 한글명 | 투자 일기 생성 |
| 발생 조건 | 투자 일기 템플릿으로 새 메모가 정상 생성된 시점 |
| 화면 | 대시보드, 메모 생성 흐름 |
| 주요 정보 | `note_id`, `journal_date`, `source`, `template_key`, `is_first_journal` |
| 사용자 구분 | 가입일, 기기, 누적 투자 일기 수 |
| 분석 목적 | 사용자가 기록 루틴을 시작하는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 이벤트 수와 `notes` 테이블의 투자 일기 생성 수 비교 |

판단할 수 있는 것:

- 가입자가 실제로 첫 기록을 만들었는지
- 대시보드의 “오늘 기록” 버튼이 기록 생성으로 이어지는지
- 특정 사용자가 며칠 동안 투자 일기를 만들었는지

주의할 점:

- 이 이벤트만으로 “실제로 글을 썼다”고 판단하면 안 됩니다.
- 템플릿이 들어간 빈 메모도 생성될 수 있기 때문입니다.

### 8.2 투자 일기 실제 작성

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 템플릿만 열고 나간 것이 아니라 자기 생각을 남겼는가 |
| 이벤트명 | `investment_journal_edited` |
| 한글명 | 투자 일기 실제 작성 |
| 발생 조건 | 투자 일기에서 템플릿 대비 변경된 글자 수가 20자 이상이 된 시점 |
| 화면 | 메모 작성 |
| 주요 정보 | `note_id`, `journal_date`, `source`, `delta_text_length_bucket` |
| 사용자 구분 | 가입일, 기기, 누적 투자 일기 수 |
| 분석 목적 | 투자 일기 생성에서 실제 작성까지 이어지는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 새 메모 생성 후 20자 이상 작성한 테스트와 이벤트 발생 비교 |

20자 기준:

- 전체 본문 길이가 아니라 템플릿 대비 사용자가 추가하거나 수정한 글자 수입니다.
- 같은 투자 일기에서는 최초 1회만 기록합니다.
- 이후 더 길게 수정하더라도 같은 이벤트를 계속 쌓지 않습니다.

이 이벤트로 알 수 있는 것:

- 사용자가 “투자 일기 작성”이라는 핵심 행동을 실제로 했는지
- 대시보드 방문자 중 몇 명이 의미 있는 기록까지 갔는지
- 매일 기록 습관이 생기는지

### 8.3 다시 볼 메모 열기

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 1주/3개월/1년 뒤 복기 대상 메모를 실제로 여는가 |
| 이벤트명 | `due_review_note_opened` |
| 한글명 | 다시 볼 메모 열기 |
| 발생 조건 | 다시 볼 기록 목록이나 대시보드에서 복기 대상 메모를 연 시점 |
| 화면 | 다시 볼 기록, 메모 작성 |
| 주요 정보 | `note_id`, `review_schedule_id`, `review_type`, `due_date`, `days_overdue`, `source` |
| 사용자 구분 | 가입일, 기기, 누적 투자 일기 수 |
| 분석 목적 | 1주/3개월/1년 복기 알림이 실제 열람으로 이어지는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 복기 대상 메모를 열 때 이벤트가 1회 발생하는지 확인 |

`review_type` 값:

- `1w`: 1주 뒤 복기
- `3m`: 3개월 뒤 복기
- `1y`: 1년 뒤 복기

이 이벤트로 알 수 있는 것:

- 사용자가 다시 볼 기록을 발견하고 열어보는지
- `1w`, `3m`, `1y` 중 어떤 복기 주기가 더 잘 열리는지
- 복기 예정일보다 며칠 뒤에 열어보는지

주의할 점:

- 이 이벤트는 “열었다”는 뜻입니다.
- 복기 내용을 썼는지는 `due_review_note_edited`로 따로 봐야 합니다.

### 8.4 다시 볼 메모 수정

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 과거 판단을 다시 보고 새 생각을 남기는가 |
| 이벤트명 | `due_review_note_edited` |
| 한글명 | 다시 볼 메모 수정 |
| 발생 조건 | 복기 대상 메모를 연 뒤, 진입 시점 대비 변경된 글자 수가 20자 이상이 된 시점 |
| 화면 | 메모 작성 |
| 주요 정보 | `note_id`, `review_schedule_id`, `review_type`, `delta_text_length_bucket` |
| 사용자 구분 | 가입일, 기기, 누적 투자 일기 수 |
| 분석 목적 | 다시 보기에서 실제 복기 작성으로 이어지는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 복기 대상 메모를 열고 20자 이상 수정했을 때 이벤트가 발생하는지 확인 |

20자 기준:

- 메모 전체 길이가 아니라 복기 대상으로 열었을 때의 본문 대비 변경량입니다.
- 기존에 긴 메모였더라도 새로 수정한 내용이 20자 미만이면 기록하지 않습니다.
- 같은 `review_schedule_id`에서는 최초 1회만 기록합니다.

이 이벤트로 알 수 있는 것:

- 사용자가 과거 판단을 읽고 현재 생각을 덧붙이는지
- 단순 열람과 실제 복기를 구분할 수 있습니다.
- 1주/3개월/1년 복기 중 어떤 주기가 실제 작성까지 이어지는지 볼 수 있습니다.

### 8.5 다시 볼 복기 완료

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 1주/3개월/1년 복기를 끝냈다고 처리하는가 |
| 이벤트명 | `due_review_completed` |
| 한글명 | 다시 볼 복기 완료 |
| 발생 조건 | 복기 완료 버튼이 정상 처리되어 일정 상태가 `completed`가 된 시점 |
| 화면 | 메모 작성 |
| 주요 정보 | `note_id`, `review_schedule_id`, `review_type`, `due_date`, `days_overdue` |
| 사용자 구분 | 가입일, 기기, 누적 투자 일기 수 |
| 분석 목적 | 복기 대상 열람에서 완료 처리까지 이어지는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 이벤트 수와 `review_schedules.status = completed` 수 비교 |

이 이벤트로 알 수 있는 것:

- 사용자가 복기를 완료 처리할 만큼 흐름을 이해했는지
- “다시 볼 기록”이 쌓이기만 하고 방치되는지
- 복기 완료 버튼의 위치나 문구가 충분히 잘 보이는지

### 8.6 이번 주 복기 열기

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 이번 주 작성한 기록을 모아보는가 |
| 이벤트명 | `weekly_review_opened` |
| 한글명 | 이번 주 복기 열기 |
| 발생 조건 | 이번 주 복기 화면이 정상 로드된 시점 |
| 화면 | 대시보드, 주간 복기 |
| 주요 정보 | `review_id`, `week_start`, `week_end`, `source_note_count`, `entry_mode`, `day_of_week`, `is_weekend` |
| 사용자 구분 | 가입일, 기기, 이번 주 투자 일기 수 |
| 분석 목적 | 매일 기록이 주간 정리로 이어지는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 대시보드 버튼 클릭 후 이벤트 발생 확인 |

`entry_mode` 값:

- `start`: 이번 주 복기를 처음 만든 경우
- `resume`: 이미 만든 이번 주 복기를 이어서 여는 경우

날짜 기준에 대한 판단:

- 주간 복기는 아무 때나 쓸 수 있으므로, 성공 기준을 토요일/일요일로 제한하지 않습니다.
- 대신 `day_of_week`, `is_weekend`를 속성으로만 남깁니다.
- 이렇게 하면 “사용자들이 실제로 주말에 많이 쓰는지”를 나중에 볼 수 있습니다.

이 이벤트로 알 수 있는 것:

- 사용자가 주간 복기 기능을 발견했는지
- 이번 주 기록이 몇 개 있을 때 주간 복기를 여는지
- 주말에 더 많이 쓰는지, 평일에도 쓰는지

### 8.7 이번 주 복기 실제 작성

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 이번 주 기록을 읽고 회고를 남기는가 |
| 이벤트명 | `weekly_review_edited` |
| 한글명 | 이번 주 복기 실제 작성 |
| 발생 조건 | 주간 복기에서 템플릿 대비 변경된 글자 수가 20자 이상이 된 시점 |
| 화면 | 주간 복기 |
| 주요 정보 | `review_id`, `week_start`, `week_end`, `source_note_count`, `delta_text_length_bucket`, `day_of_week`, `is_weekend` |
| 사용자 구분 | 가입일, 기기, 이번 주 투자 일기 수 |
| 분석 목적 | 주간 복기 열람에서 실제 회고 작성까지 이어지는지 확인 |
| 우선순위 | 필수 |
| 검증 방법 | 주간 복기에서 20자 이상 작성했을 때 이벤트 발생 확인 |

20자 기준:

- 전체 본문 길이가 아니라 주간 복기 템플릿 대비 사용자가 추가/수정한 글자 수입니다.
- 같은 `review_id`에서는 최초 1회만 기록합니다.

이 이벤트로 알 수 있는 것:

- 사용자가 이번 주 기록을 읽고 실제 정리를 남기는지
- 투자 일기 수가 많을수록 주간 복기 작성률이 올라가는지
- 주말에 작성률이 더 높은지

주의할 점:

- 이번 주 복기에는 별도 완료 버튼을 두지 않습니다.
- 자동 저장되는 작성 화면이므로, 사용자가 20자 이상 실제 회고를 남겼는지를 핵심 기준으로 봅니다.

### 8.8 복기 중 대표 메모 열기

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 복기 중 대표 메모를 참고하는가 |
| 이벤트명 | `pinned_note_opened_from_review` |
| 한글명 | 복기 중 대표 메모 열기 |
| 발생 조건 | 주간 복기 또는 1주/3개월/1년 복기 흐름에서 대표 메모를 연 시점 |
| 화면 | 주간 복기, 메모 작성 |
| 주요 정보 | `note_id`, `review_context`, `source` |
| 사용자 구분 | 가입일, 기기, 대표 메모 보유 여부 |
| 분석 목적 | 복기가 대표 메모 확인으로 이어지는지 확인 |
| 우선순위 | 중요 |
| 검증 방법 | 복기 화면에서 대표 메모 진입 시 이벤트 발생 확인 |

`review_context` 값:

- `weekly_review`
- `due_review_1w`
- `due_review_3m`
- `due_review_1y`

이 이벤트로 알 수 있는 것:

- 대표 메모가 단순 고정 메모인지, 복기 중 참고되는 도구인지
- 사용자가 자신의 원칙이나 체크리스트를 복기 과정에서 다시 보는지

### 8.9 복기 중 대표 메모 수정

| 항목 | 내용 |
| --- | --- |
| 확인하려는 질문 | 사용자가 복기 후 대표 메모를 고치며 자기 원칙을 업데이트하는가 |
| 이벤트명 | `pinned_note_updated_from_review` |
| 한글명 | 복기 중 대표 메모 수정 |
| 발생 조건 | 복기 흐름에서 대표 메모를 연 뒤, 진입 시점 대비 변경된 글자 수가 20자 이상이 된 시점 |
| 화면 | 메모 작성 |
| 주요 정보 | `note_id`, `review_context`, `delta_text_length_bucket` |
| 사용자 구분 | 가입일, 기기, 대표 메모 보유 여부 |
| 분석 목적 | 복기가 투자 세계관/행동 원칙 수정으로 이어지는지 확인 |
| 우선순위 | 중요 |
| 검증 방법 | 복기에서 대표 메모를 열고 20자 이상 수정했을 때 이벤트 발생 확인 |

20자 기준:

- 대표 메모 전체 길이가 아니라, 복기 흐름에서 열었을 때의 본문 대비 변경량입니다.
- 같은 대표 메모라도 일반 폴더에서 수정한 것은 이 이벤트로 보지 않습니다.
- “복기 중 대표 메모를 고쳤다”는 맥락이 중요하기 때문입니다.

이 이벤트로 알 수 있는 것:

- 복기가 단순 회고에서 끝나는지
- 복기 후 실제로 자기 투자 원칙을 업데이트하는지
- 대표 메모가 “내 투자 운영체제” 역할을 하는지

아래 이벤트는 나중에 필요하면 추가합니다.

- 버튼 클릭보다 실제 생성, 실제 작성, 실제 수정이 더 강한 행동입니다.

## 11. 이벤트 구현 시 주의할 점

### 11.1 템플릿을 작성으로 오인하지 않기

가장 중요한 주의점입니다.

투자 일기와 주간 복기는 처음 생성될 때 템플릿 내용이 이미 들어갑니다. 따라서 단순히 `content_text.length >= 20`으로 판단하면 안 됩니다.

올바른 방식:

1. 메모 생성 시점의 기본 템플릿 글자 수를 기준점으로 둡니다.
2. 사용자가 작성한 뒤 현재 글자 수와 기준점의 차이를 계산합니다.
3. 차이가 20자 이상일 때 작성 이벤트를 기록합니다.

또는:

1. 메모 화면에 들어온 시점의 본문 글자 수를 기준점으로 둡니다.
2. 이후 자동저장 시 현재 본문과 비교합니다.
3. 변경량이 20자 이상이면 수정 이벤트를 기록합니다.

### 11.2 자동저장 중복 기록 방지

메모는 자동저장됩니다. 사용자가 한 문장을 쓰는 동안 저장이 여러 번 발생할 수 있습니다.

따라서 같은 대상에서는 최초 1회만 기록합니다.

예시:

- 같은 투자 일기에서 `investment_journal_edited`는 1회만 기록
- 같은 복기 일정에서 `due_review_note_edited`는 1회만 기록
- 같은 주간 복기에서 `weekly_review_edited`는 1회만 기록
- 같은 복기 맥락에서 대표 메모 수정은 1회만 기록

### 11.3 본문 저장 금지

분석 이벤트에는 본문을 저장하지 않습니다.

나중에 알고 싶은 것은 “무엇을 썼는지”가 아니라 “복기 루틴이 작동했는지”입니다.

저장해도 되는 것:

- 이벤트명
- 사용자 ID
- 메모 ID
- 복기 타입
- 글자 수 구간
- 진입 경로
- 발생 시각

저장하면 안 되는 것:

- 사용자가 쓴 문장
- 종목명
- 금액
- 계좌 정보
- 투자 판단의 상세 내용

## 12. 권장 테이블 형태

추후 구현 시 Supabase에 아래처럼 이벤트 테이블을 둘 수 있습니다.

```sql
create table public.analytics_events (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  event_name text not null,
  page_path text,
  properties jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);
```

RLS 원칙:

- 일반 사용자는 자기 이벤트만 생성할 수 있게 합니다.
- 일반 사용자가 다른 사용자의 이벤트를 읽지 못하게 합니다.
- 운영자가 집계할 때는 서버 권한 또는 관리자용 쿼리로 봅니다.

이 테이블은 “카운팅용 기록장”에 가깝습니다. 사용자가 버튼을 누르거나 20자 이상 작성하는 순간, 그 사실을 한 줄씩 남기는 방식입니다.

## 13. 최종 판단 기준

복기노트가 잘 작동하고 있는지 판단할 때 가장 중요한 흐름은 아래입니다.

1. 사용자가 투자 일기를 만든다.
2. 템플릿 위에 자기 생각을 20자 이상 남긴다.
3. 시간이 지난 뒤 1주/3개월/1년 복기 대상 메모를 연다.
4. 과거 판단을 보고 20자 이상 새 생각을 남긴다.
5. 이번 주 기록을 모아 주간 복기를 연다.
6. 주간 복기에도 20자 이상 회고를 남긴다.
7. 복기 과정에서 대표 메모를 열고, 필요하면 20자 이상 수정한다.

이 흐름이 반복되면 사용자는 단순히 메모를 쓰는 것이 아니라, 투자 판단을 다시 보고 자기 원칙을 다듬는 방향으로 가고 있다고 볼 수 있습니다.

반대로 어느 단계에서 많이 끊기는지 보면 다음 개선 방향을 정할 수 있습니다.

| 끊기는 지점 | 의심할 수 있는 문제 |
| --- | --- |
| 투자 일기 생성 전 | 대시보드의 시작 버튼이나 목적 설명이 약함 |
| 투자 일기 생성 후 작성 전 | 템플릿 질문이 어렵거나 작성 부담이 큼 |
| 다시 볼 메모 열기 전 | 복기 대상이 잘 보이지 않거나 복기 필요성이 약함 |
| 다시 볼 메모 열람 후 수정 전 | 과거 메모를 보고 무엇을 써야 할지 모름 |
| 주간 복기 열기 전 | 주간 복기의 가치가 충분히 드러나지 않음 |
| 주간 복기 열람 후 작성 전 | 한 주를 정리하는 질문이 길거나 부담스러움 |
| 대표 메모 수정 전 | 복기와 투자 원칙 업데이트가 아직 연결되지 않음 |

## 14. 이번 문서의 결론

이번 이벤트 설계의 핵심은 아래입니다.

- Vercel Analytics는 페이지 방문을 봅니다.
- 앱 이벤트는 실제 행동을 봅니다.
- 실제 행동 중에서도 “투자 복기 루틴”에 직접 연결되는 것만 우선 봅니다.
- 작성/수정 기준은 모두 `20자 이상`으로 통일합니다.
- 템플릿 글자 수는 작성으로 보지 않습니다.
- 본문 내용은 저장하지 않고, 행동 사실과 최소 속성만 저장합니다.

이 기준을 따르면 나중에 “사용자가 많이 들어왔는가?”가 아니라 “사용자가 투자 일기를 쓰고, 다시 보고, 주간 복기를 하고, 자기 원칙을 업데이트하는가?”를 볼 수 있습니다.
