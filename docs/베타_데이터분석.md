# 베타 데이터 분석 가이드

복기노트 베타 테스트에서 볼 데이터와 해석 기준을 정리한 문서입니다.

목표는 사용자를 감시하는 것이 아니라, 사람들이 투자 기록과 복기를 실제 습관으로 이어가는지 확인하는 것입니다.

## 1. 분석 원칙

- 본문 내용보다 행동 흐름을 먼저 본다.
- 이메일과 투자 판단 본문을 함께 분석하지 않는다.
- 사용자가 쓴 종목, 금액, 감정 기록은 민감할 수 있으므로 꼭 필요한 경우가 아니면 열람하지 않는다.
- 베타 초반에는 정교한 지표보다 막히는 지점을 찾는 것이 중요하다.
- 숫자만으로 판단하지 않고, 이상한 지점은 사용자 인터뷰나 피드백으로 확인한다.

## 2. 지금 사용할 도구

### Vercel Web Analytics

페이지 단위 흐름을 봅니다.

확인할 것:

- `/login`에 몇 명 들어왔는지
- `/dashboard`까지 몇 명 도달했는지
- `/notes/...` 메모 작성 화면을 얼마나 방문했는지
- `/reviews/...` 복기 화면을 얼마나 방문했는지
- 모바일과 데스크탑 비중
- 어느 페이지에서 이탈이 많은지

주의:

- 버튼 클릭 수나 작성 완료 여부는 기본 Web Analytics만으로 정확히 알기 어렵다.
- 이 단계에서는 페이지 흐름을 보는 용도로만 사용한다.

### Supabase SQL

실제 사용 행동을 봅니다.

확인할 것:

- 가입자 수
- 메모를 작성한 사람 수
- 투자 일기를 반복해서 쓴 사람 수
- 주간 복기를 만든 사람 수
- 대표 메모를 고정한 사람 수
- 다시 볼 기록이 생성되고 완료되는지

## 3. 베타 핵심 지표

처음에는 아래 5개만 매주 확인해도 충분합니다.

1. 가입자 수
2. 가입 후 메모를 1개 이상 작성한 사용자 수
3. 투자 일기를 2개 이상 작성한 사용자 수
4. 주간 복기를 1개 이상 만든 사용자 수
5. 대표 메모를 1개 이상 고정한 사용자 수

이 5개를 보면 사용자가 단순히 들어온 것인지, 실제 복기 습관으로 넘어가고 있는지 알 수 있습니다.

## 4. Supabase SQL 예시

Supabase Dashboard → SQL Editor에서 실행합니다.

### 전체 가입자 수

```sql
select count(*) as users
from public.profiles;
```

### 날짜별 가입자 수

```sql
select
  date(created_at) as day,
  count(*) as users
from public.profiles
group by 1
order by 1 desc;
```

### 메모를 1개 이상 작성한 사용자 수

```sql
select count(distinct user_id) as active_writers
from public.notes
where deleted_at is null
  and is_draft is false;
```

### 사용자별 작성 메모 수

```sql
select
  user_id,
  count(*) as note_count,
  max(updated_at) as last_note_at
from public.notes
where deleted_at is null
  and is_draft is false
group by user_id
order by note_count desc;
```

### 투자 일기를 2개 이상 작성한 사용자 수

```sql
select count(*) as repeat_investment_journal_users
from (
  select n.user_id
  from public.notes n
  join public.templates t on t.id = n.template_id
  where n.deleted_at is null
    and n.is_draft is false
    and t.template_kind = 'investment_journal'
  group by n.user_id
  having count(*) >= 2
) users;
```

### 날짜별 투자 일기 작성 수

```sql
select
  n.note_date,
  count(*) as investment_journals
from public.notes n
join public.templates t on t.id = n.template_id
where n.deleted_at is null
  and n.is_draft is false
  and t.template_kind = 'investment_journal'
group by n.note_date
order by n.note_date desc;
```

### 주간 복기를 1개 이상 만든 사용자 수

```sql
select count(distinct user_id) as weekly_review_users
from public.review_sessions
where deleted_at is null
  and is_draft is false;
```

### 사용자별 주간 복기 수

```sql
select
  user_id,
  count(*) as review_count,
  max(updated_at) as last_review_at
from public.review_sessions
where deleted_at is null
  and is_draft is false
group by user_id
order by review_count desc;
```

### 대표 메모를 고정한 사용자 수

```sql
select count(distinct user_id) as pinned_users
from public.notes
where deleted_at is null
  and is_pinned is true;
```

### 다시 볼 기록 상태

```sql
select
  status,
  count(*) as count
from public.review_schedules
group by status
order by status;
```

### 기간별 다시 볼 기록 상태

```sql
select
  review_type,
  status,
  count(*) as count
from public.review_schedules
group by review_type, status
order by review_type, status;
```

### 최근 7일 동안 실제 작성이 있었던 사용자

```sql
select count(distinct user_id) as active_users_7d
from public.notes
where deleted_at is null
  and is_draft is false
  and updated_at >= now() - interval '7 days';
```

### 가입 후 아무 메모도 작성하지 않은 사용자 수

```sql
select count(*) as signup_only_users
from public.profiles p
where not exists (
  select 1
  from public.notes n
  where n.user_id = p.id
    and n.deleted_at is null
    and n.is_draft is false
);
```

## 5. 해석 기준

### 가입은 있는데 메모 작성이 적다

가능한 원인:

- 첫 화면에서 무엇을 해야 하는지 명확하지 않다.
- 투자 일기 작성 버튼이 부담스럽다.
- 가입 직후 템플릿의 질문이 너무 많거나 어렵다.

확인 질문:

- 처음 들어왔을 때 바로 무엇을 해야 할지 알았나요?
- 투자 일기 작성 버튼을 누르기 전에 망설인 이유가 있나요?

### 메모는 쓰지만 주간 복기를 안 한다

가능한 원인:

- 이번 주 복기의 의미가 충분히 명확하지 않다.
- 기록을 다시 읽는 흐름이 아직 보상처럼 느껴지지 않는다.
- 주간 복기 템플릿이 부담스럽거나 길다.

확인 질문:

- 이번 주 복기가 어떤 기능인지 이해됐나요?
- 기록을 다시 읽고 정리하는 과정이 자연스러웠나요?

### 주간 복기는 만들지만 대표 메모를 안 쓴다

가능한 원인:

- 대표 메모가 투자 원칙을 쌓는 곳이라는 의미가 약하다.
- 복기에서 깨달은 내용을 원칙으로 옮기는 연결이 부족하다.

확인 질문:

- 대표 메모가 무엇을 위한 곳인지 이해됐나요?
- 복기 중 발견한 내용을 따로 남기고 싶다는 생각이 들었나요?

### 다시 볼 기록이 완료되지 않는다

가능한 원인:

- 1주, 3개월, 1년 복기의 가치가 아직 체감되지 않는다.
- 다시 볼 기록이 숙제처럼 느껴진다.
- 완료 버튼이나 완료 기준이 명확하지 않다.

확인 질문:

- 다시 볼 기록을 눌렀을 때 무엇을 해야 할지 알았나요?
- 완료 처리가 자연스러웠나요?

## 6. 매주 확인 루틴

베타 기간에는 일주일에 한 번 아래 순서로 확인합니다.

1. Vercel Web Analytics에서 `/login → /dashboard → /notes 또는 /reviews` 흐름을 본다.
2. Supabase SQL로 핵심 지표 5개를 확인한다.
3. 가장 많이 끊기는 지점을 하나만 고른다.
4. 해당 지점에 대한 사용자 피드백을 2~3명에게 묻는다.
5. 기능 추가보다 문구, 위치, 흐름 개선으로 먼저 해결할 수 있는지 본다.

## 7. 다음 단계에서 추가할 수 있는 이벤트 추적

지금은 필수는 아닙니다.

나중에 더 정확히 보고 싶다면 아래 행동을 이벤트로 남길 수 있습니다.

- 투자 일기 작성 버튼 클릭
- 오늘 기록 생성 완료
- 오늘 기록 이어쓰기 클릭
- 이번 주 복기 시작 클릭
- 이번 주 복기 이어쓰기 클릭
- 다시 볼 기록 클릭
- 다시 볼 기록 복기 완료 클릭
- 대표 메모 고정 클릭
- 템플릿 수정 저장

이벤트 추적은 개인정보를 최소화해야 합니다.

저장해도 되는 예:

- `user_id`
- `event_name`
- `created_at`
- `page_path`

주의할 것:

- 메모 본문
- 종목명
- 투자 금액
- 사용자가 적은 감정 문장

이런 정보는 이벤트 로그에 넣지 않습니다.

## 8. 지금 결론

현재 단계에서는 아래 방식이 가장 가볍고 안전합니다.

- 페이지 이동 흐름은 Vercel Web Analytics로 본다.
- 실제 작성과 복기 행동은 Supabase SQL로 본다.
- 본문 내용은 보지 않고 행동 숫자부터 본다.
- 숫자에서 막히는 지점을 찾고, 그 지점만 사용자에게 물어본다.
