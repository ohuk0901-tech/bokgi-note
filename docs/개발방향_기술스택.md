# 개발 방향 및 기술 스택

## 1. 개발자 검토 결론

이 서비스는 처음부터 모바일 앱으로 만들기보다 웹/PWA로 먼저 만드는 것이 적합하다.

이유는 다음과 같다.

- 핵심 기능이 앱스토어 배포보다 "여러 메모와 복기 세션을 한 화면에서 읽으며 새 복기를 작성하는 경험"에 있기 때문이다.
- 웹/PWA는 빠르게 만들고 배포할 수 있어 3개월 MVP 검증에 유리하다.
- 나중에 모바일 앱을 만들더라도 같은 데이터베이스와 로그인 시스템을 그대로 사용할 수 있다.
- 투자 추천, 수익률 분석, 증권사 연동이 아니라 메모/복기/누적 회고가 핵심이므로 복잡한 네이티브 기능이 초기에 필요하지 않다.

따라서 권장 방향은 다음과 같다.

```text
1단계: 웹/PWA MVP
2단계: 사용성 개선, 검색, 백업, 오프라인 보완
3단계: Expo/React Native 기반 모바일 앱
4단계: AI 복기 보조 기능 추가
```

## 2. 서비스의 현재 정의

이 서비스는 투자 일기를 중심으로 시작하지만, 본질적으로는 "복기 세션이 누적되는 메모 앱"이다.

사용자는 평소처럼 메모를 작성한다. 이후 여러 개의 메모 또는 과거 복기 세션을 선택해 복기 모드에 들어가면, 선택된 원본 항목들이 하나의 긴 흐름처럼 표시된다. 사용자는 그 흐름을 읽으면서 새 복기 세션을 작성하고, 필요하면 기존 메모를 최대 3개까지 불러와 수정할 수 있다.

초기 목적은 투자 일기 복기이다. 다만 구조 자체는 일기, 업무일지, 공부 기록, 프로젝트 회고 등으로 확장 가능해야 한다.

## 3. 핵심 UX 원칙

1. 일반 메모와 복기 세션을 내부적으로 구분한다.
2. 목록에서는 일반 메모와 복기 세션을 함께 최신 등록순으로 보여준다.
3. 복기 세션은 제목 옆 `복기` 뱃지로 구분한다.
4. 일반 메모와 과거 복기 세션 모두 새 복기의 원본으로 선택할 수 있다.
5. 복기 모드에 들어간 원본 항목은 읽기 전용으로 보여준다.
6. 복기 입력창은 화면 맨 아래에만 고정하지 않고 원본 항목 사이로 이동할 수 있어야 한다.
7. 복기 중 기존 메모를 최대 3개까지 불러와 수정할 수 있어야 한다.
8. 저장 버튼 없이 자동 저장하고 `저장 중`, `저장됨`, `저장 실패` 상태를 보여준다.
9. 서비스는 사용자의 판단을 평가하거나 투자 결정을 대신하지 않는다.

## 4. 권장 기술 스택

| 영역 | 선택 | 쉬운 설명 | 선택 이유 |
|---|---|---|---|
| 프론트엔드 | Next.js | 웹앱의 화면과 페이지를 만드는 도구 | 웹/PWA MVP를 빠르게 만들고 나중에 확장하기 좋다 |
| UI 구성 | React | 버튼, 메모 카드, 에디터 같은 화면 조각을 만드는 방식 | 나중에 React Native 모바일 앱으로 넘어갈 때 사고방식이 이어진다 |
| 언어 | TypeScript | 실수를 줄여주는 JavaScript | 메모, 복기 세션, 사용자 같은 데이터 구조를 안전하게 다루기 좋다 |
| 디자인 | Tailwind CSS | 화면 스타일을 빠르게 적용하는 도구 | 아이폰 메모장 같은 단순한 UI를 빠르게 만들기 좋다 |
| 백엔드 | Next.js Route Handlers / Server Actions | 화면 뒤에서 저장, 수정, AI 요청 등을 처리하는 코드 | 별도 서버를 처음부터 만들지 않아도 된다 |
| 데이터베이스 | Supabase Postgres | 메모와 복기 데이터를 저장하는 관계형 데이터베이스 | 메모, 복기 세션, 원본 연결 구조에 잘 맞는다 |
| 인증 | Supabase Auth | 로그인 기능 | 베타/MVP에서는 이메일/비밀번호만 제공한다 |
| 배포 | Vercel | 만든 웹앱을 인터넷에 올리는 서비스 | Next.js 배포와 궁합이 좋고 MVP 배포가 쉽다 |
| 모바일 앱 | Expo / React Native | iPhone/Android 앱을 만드는 도구 | 웹에서 사용한 React 방식과 이어지고 Supabase를 그대로 사용할 수 있다 |
| AI | OpenAI API | 복기 질문, 요약, 패턴 정리 등을 도와주는 AI | MVP 이후 복기 보조 기능으로 붙이기 좋다 |

## 5. 왜 이 스택이 이 서비스에 맞는가

이 서비스는 단순 메모 앱처럼 보이지만 실제로는 데이터 사이의 관계가 중요하다.

예를 들어 사용자는 다음과 같은 일을 한다.

```text
월요일 투자 일기
화요일 투자 일기
수요일 투자 일기
목요일 투자 일기
금요일 투자 일기
토요일 투자 일기

위 6개 메모를 선택
-> 주간 복기 세션 생성

4개의 주간 복기 세션을 선택
-> 월간 복기 세션 생성
```

이 구조는 "메모 하나 저장"이 아니라 "메모와 복기 세션이 다시 다른 복기의 재료가 되는 구조"이다. 그래서 관계형 데이터베이스인 Postgres가 자연스럽다.

Supabase는 Postgres를 기반으로 하면서 인증, 권한, API 사용을 쉽게 제공하므로 3개월 MVP에 적합하다.

## 6. PWA의 의미와 역할

PWA는 Progressive Web App의 약자이다.

쉽게 말하면 "앱처럼 설치할 수 있는 웹사이트"이다.

일반 웹앱 사용 흐름:

```text
브라우저 열기
-> 주소 입력
-> 서비스 접속
```

PWA 사용 흐름:

```text
홈 화면의 앱 아이콘 터치
-> 앱처럼 실행
```

초기에는 앱스토어 심사를 거치지 않고도 아이폰이나 안드로이드 홈 화면에서 앱처럼 사용할 수 있다. 다만 iOS/Android의 모든 네이티브 기능을 자유롭게 쓰는 것은 아니므로, 정식 모바일 앱이 필요해지는 시점에는 Expo/React Native로 확장한다.

MVP에서는 PWA 설치 지원은 포함하지만 완전한 오프라인 작성은 제외한다. 오프라인 작성은 자동 저장, 로그인, 동기화, 충돌 해결을 함께 설계해야 하므로 초기 복잡도를 크게 올린다.

## 7. 나중에 모바일 앱으로 확장하는 방식

처음 웹/PWA에서 만든 데이터베이스와 로그인은 나중 모바일 앱에서도 그대로 사용한다.

```text
Next.js 웹/PWA
        |
        v
Supabase Auth + Supabase Postgres
        ^
        |
Expo / React Native 모바일 앱
```

이렇게 하면 모바일 앱을 만들 때 모든 것을 처음부터 다시 만들 필요가 없다. 모바일 앱에서는 화면만 모바일에 맞게 새로 만들고, 로그인과 데이터 저장은 기존 Supabase를 사용한다.

모바일 확장을 고려해 초기 MVP부터 지켜야 할 원칙:

- 비즈니스 로직을 화면 코드에만 흩뿌리지 않는다.
- 데이터 구조를 명확하게 설계한다.
- Supabase 테이블과 권한 정책을 기준으로 사용자 데이터를 분리한다.
- 웹 전용 UI와 서비스 핵심 로직을 가능한 한 분리한다.
- API 응답 구조를 모바일에서도 재사용할 수 있게 단순하게 유지한다.

## 8. 권장 데이터 모델 초안

아래는 MVP 기준의 초안이다. 실제 개발 시 Supabase 마이그레이션 파일로 구체화한다.

### auth.users

Supabase Auth의 기본 사용자 정보를 사용한다. 별도 사용자 테이블은 필요한 프로필 정보가 생길 때 만든다.

이메일/비밀번호 가입은 이메일 인증을 필수로 한다. Google 로그인은 베타/MVP에서 제외한다.

### profiles

서비스 계정 상태와 삭제 요청 상태를 저장한다.

주요 필드:

```text
id
email
display_name
deletion_requested_at
delete_after
created_at
updated_at
```

구현 규칙:

- `id`는 Supabase Auth 사용자 ID와 동일하게 사용한다.
- 첫 가입 또는 첫 로그인 시 `profiles` 행과 기본 폴더를 함께 생성한다.
- 계정 삭제를 요청하면 `deletion_requested_at`과 `delete_after`를 기록하고 사용자를 로그아웃시킨다.
- 삭제 요청 상태의 사용자가 다시 접근하면 앱 화면 진입을 차단한다.

### folders

1단 폴더를 저장한다.

주요 필드:

```text
id
user_id
name
sort_order
created_at
updated_at
deleted_at
delete_after
```

MVP에서는 중첩 폴더를 만들지 않는다.

신규 사용자의 첫 가입 또는 첫 로그인 시 `기본` 폴더를 자동 생성한다.

폴더를 휴지통으로 이동하면 폴더 안의 일반 메모와 복기 세션도 함께 휴지통으로 이동한다.

### notes

일반 메모를 저장한다.

예시:

- 월요일 투자 일기
- 투자 원칙
- 매수 체크리스트
- 다음에 확인할 것

주요 필드:

```text
id
user_id
folder_id
title
content
note_date
is_draft
created_at
updated_at
deleted_at
delete_after
```

MVP에서는 `tags`, `note_type`, `note_versions`를 사용하지 않는다.

초안 생성 규칙:

- 폴더 상세 화면에서 `+` 버튼을 누르면 즉시 `notes` 행을 만든다.
- 기본 제목은 `제목 없음`이다.
- 기본 날짜는 오늘 날짜이다.
- `is_draft`는 처음 생성 시 `true`로 둔다.
- 사용자가 제목을 바꾸거나 본문을 입력하면 `is_draft`를 `false`로 바꾼다.
- 사용자가 화면을 나갈 때 제목이 `제목 없음`이고 본문이 비어 있으면 빈 초안으로 보고 자동 삭제한다.

### review_sessions

복기 결과를 저장한다.

복기 세션은 내부적으로 일반 메모와 구분한다. 사용자 화면에서는 폴더 목록에 일반 메모처럼 최신 등록순으로 표시하고 제목 옆에 `복기` 뱃지를 붙인다.

주요 필드:

```text
id
user_id
folder_id
title
content
review_date
editor_position
is_draft
created_at
updated_at
deleted_at
delete_after
```

복기 세션은 나중에 다시 열어 수정할 수 있다.

초안 생성 규칙:

- 복기 작성 화면에 진입하면 즉시 `review_sessions` 행을 만든다.
- 기본 제목은 `YYYY.MM.DD 복기` 형식이다.
- 기본 복기 날짜는 오늘 날짜이다.
- `is_draft`는 처음 생성 시 `true`로 둔다.
- 사용자가 제목을 바꾸거나 복기 본문을 입력하면 `is_draft`를 `false`로 바꾼다.
- 사용자가 화면을 나갈 때 제목이 기본값이고 본문이 비어 있으면 빈 복기 초안으로 보고 자동 삭제한다.

### review_sources

복기 세션에 포함된 원본 항목을 저장한다.

원본 항목은 일반 메모 또는 과거 복기 세션일 수 있다.

권장 필드:

```text
id
review_session_id
source_note_id
source_review_session_id
sort_order
created_at
```

구현 규칙:

- `source_note_id`와 `source_review_session_id` 중 하나만 값이 있어야 한다.
- 둘 다 비어 있거나 둘 다 값이 있으면 안 된다.
- 복기 원본은 최대 6개까지 선택할 수 있다.
- 원본 스냅샷은 저장하지 않는다.
- 복기 세션을 다시 열면 원본 항목은 항상 최신 내용을 보여준다.
- 원본 정렬은 일반 메모의 `note_date`와 복기 세션의 `review_date`를 공통 날짜로 보고 오래된 순으로 처리한다.

### editable_review_notes

복기 중 불러와 수정할 기존 메모 연결을 저장한다.

복기 세션을 다시 열었을 때 어떤 기존 메모를 함께 불러왔는지 재현하기 위해 MVP에 포함한다.

```text
id
review_session_id
note_id
sort_order
created_at
```

복기 중 불러와 수정할 기존 메모는 최대 3개까지 허용한다.

## 9. 목록과 검색 설계

폴더 목록은 `notes`와 `review_sessions`를 합쳐 최신 등록순으로 보여준다.

목록 항목 공통 표시값:

```text
id
item_type
title
preview
display_date
created_at
updated_at
```

item_type 값:

```text
note
review_session
```

표시 규칙:

- `note`는 별도 뱃지 없이 표시한다.
- `review_session`은 제목 옆에 `복기` 뱃지를 표시한다.
- 폴더 안에서는 `created_at` 기준 최신 등록순을 MVP 기본값으로 사용한다.
- 검색은 일반 메모와 복기 세션의 제목/본문을 모두 대상으로 한다.
- MVP 검색은 Postgres `ilike` 기반의 단순 부분검색으로 시작한다.
- 검색 결과에서도 복기 세션은 `복기` 뱃지를 표시한다.

## 10. 자동 저장, 삭제, 계정 삭제 정책

### 자동 저장

저장 버튼은 두지 않는다. 메모, 복기 세션, 복기 중 불러온 기존 메모는 입력 후 짧은 지연 시간을 두고 자동 저장한다.

화면에는 다음 상태를 표시한다.

```text
저장 중
저장됨
저장 실패
```

복기 중 불러온 기존 메모는 수정 즉시 원본 메모에 자동 저장한다. 별도의 반영 버튼을 두지 않는다.

### 휴지통과 완전 삭제

삭제는 즉시 완전 삭제하지 않고 `deleted_at`과 `delete_after`를 기록하는 soft delete로 처리한다.

휴지통 항목은 `delete_after` 기준 30일 후 완전 삭제 대상이 된다.

MVP에서는 `purge_deleted_items` 정리용 서버 함수를 만든다.

구현 규칙:

- `purge_deleted_items`는 service role 권한으로만 실행한다.
- 브라우저에서 직접 호출하지 않는다.
- 운영자가 필요할 때 실행할 수 있게 만든다.
- 정식 운영 전에는 스케줄 실행으로 확장할 수 있다.

### 계정 삭제

계정 삭제 요청 시 즉시 완전 삭제하지 않는다.

처리 순서:

1. `profiles.deletion_requested_at`과 `profiles.delete_after`를 기록한다.
2. 해당 사용자의 폴더, 메모, 복기 세션, 연결 데이터를 soft delete 처리한다.
3. 사용자를 로그아웃시킨다.
4. 이후 앱 접근을 차단한다.
5. `delete_after`가 지난 뒤 정리용 서버 함수로 완전 삭제한다.

이 정책은 실수 삭제를 방지하고 30일 삭제 정책과 일관성을 맞추기 위한 것이다.

## 11. 인증 및 운영 정책

MVP 인증은 Supabase Auth를 사용한다.

포함 로그인:

- 이메일/비밀번호
- Google 로그인 제외

이메일/비밀번호 가입은 이메일 인증을 필수로 한다.

운영 정책:

- 공개 회원가입으로 시작한다.
- MVP 운영 기준은 최대 30명 베타 사용자이다.
- 서비스 언어는 한국어만 지원한다.
- 비로그인 데모는 제공하지 않는다.
- 정식 공개 전 개인정보 처리방침과 이용약관을 준비한다.

## 12. MVP 기능 범위

1. 회원가입/로그인

4. `+` 버튼을 통한 메모 작성
5. 메모 작성 및 수정
6. 자동 저장 상태 표시

10. 체크박스 기반 복기 원본 선택

13. 복기 모드에서 원본 항목 읽기 전용 표시

17. 휴지통

19. 계정 삭제

## 14. 화면 구조 초안

권장 페이지 구조:

```text
/
/login
/folders
/folders/[id]
/notes/new
/notes/[id]
/reviews/new
/reviews/[id]
/trash
/settings
```

각 화면의 역할:

| 화면 | 역할 |
|---|---|
| /login | 로그인 |
| /folders | 폴더 목록 |
| /folders/[id] | 폴더 안 메모/복기 세션 통합 목록 |
| /notes/new | 새 메모 작성 |
| /notes/[id] | 기존 메모 보기/수정 |
| /reviews/new | 복기할 원본 선택 및 복기 작성 |
| /reviews/[id] | 기존 복기 세션 보기/수정 |
| /trash | 휴지통 |
| /settings | 계정, PWA 안내, 계정 삭제 |

## 15. 복기 모드 UI 방향

복기 모드는 이 서비스의 가장 중요한 화면이다.

구성:

```text
[복기 제목]

[월요일 투자 일기]
내용...

[여기로 복기 입력창 이동]

[화요일 투자 일기]
내용...

[여기로 복기 입력창 이동]

[지난주 복기] [복기]
내용...

[복기 입력창]

[기존 메모 불러오기]
[투자 원칙 편집 영역]
[행동 원칙 편집 영역]
```

핵심 규칙:

- 원본 항목 카드에는 수정 버튼을 보여주지 않는다.
- 원본 항목은 날짜, 제목, 내용을 명확히 보여준다.
- 원본 항목이 복기 세션이면 `복기` 뱃지를 보여준다.
- 복기 입력창은 하나만 존재한다.
- "여기로 이동" 버튼 또는 화살표 버튼으로 복기 입력창 위치를 옮긴다.
- 처음부터 드래그 앤 드롭을 만들 필요는 없다.
- 기존 메모 편집 영역은 최대 3개까지만 허용한다.

## 16. AI 연동 방향

AI는 MVP 이후에 붙인다.

AI의 역할은 투자 판단이나 종목 추천이 아니라 복기 보조이다.

허용 가능한 AI 기능:

- 선택한 원본 항목을 바탕으로 복기 질문 생성
- 반복적으로 등장한 감정, 행동, 표현 정리
- 기준 메모에 추가할 만한 문장 후보 제안
- 긴 복기 세션 요약

피해야 할 AI 기능:

- 특정 종목 매수/매도 추천
- 투자 결과 평가
- 수익률 예측
- 사용자의 판단을 정답/오답으로 판정
- 금융 조언처럼 보이는 문장 생성

AI 구현 방식:

```text
사용자 클릭
-> Next.js API route
-> OpenAI API 호출
-> 결과를 화면에 제안 형태로 표시
-> 사용자가 직접 채택/수정
```

AI 결과는 자동으로 메모나 복기 세션에 반영하지 않는다. 반드시 사용자가 직접 확인하고 저장해야 한다.

## 17. 보안 및 개인정보 원칙

투자 일기와 개인 메모는 민감한 정보이다. MVP부터 아래 원칙을 지킨다.

- 모든 사용자 데이터 테이블에 `user_id`를 둔다.
- Supabase Row Level Security를 활성화한다.
- 사용자는 자신의 데이터만 읽고 쓸 수 있어야 한다.
- 서비스 역할 키는 브라우저에 노출하지 않는다.
- 삭제는 soft delete 방식으로 처리한다.
- 휴지통 항목은 `delete_after` 기준으로 30일 후 완전 삭제한다.
- 휴지통 정리는 `purge_deleted_items` 서버 함수로 처리한다.
- 계정 삭제 시 사용자 화면에서는 즉시 삭제 처리하고, 내부 데이터는 30일 후 완전 삭제 정책을 따른다.
- 정식 출시 전에는 개인정보 처리방침과 이용약관을 준비한다.
- 투자 추천 서비스처럼 보이는 문구를 피한다.

## 19. 나중에 AI가 개발할 때 따라야 할 원칙

AI가 이 프로젝트를 이어서 개발할 때는 아래 원칙을 우선한다.

1. 새 기능을 만들기 전에 이 문서와 서비스 개요를 먼저 읽는다.
2. 투자 추천 앱으로 만들지 않는다.
3. 핵심 화면은 복기 모드이다.
4. 복기 모드에서 원본 항목은 읽기 전용이다.
5. 일반 메모와 복기 세션 모두 복기 원본이 될 수 있다.
6. 복기 세션은 내부적으로 일반 메모와 구분해 저장한다.
7. 복기 세션은 목록에서 일반 메모처럼 보이되 `복기` 뱃지를 표시한다.
8. 복기 세션은 현재 폴더에 저장한다.
9. 복기 세션을 다시 열면 원본 항목은 최신 내용을 보여준다.
10. 3개월 MVP에서는 AI, 증권사 연동, 수익률 분석을 만들지 않는다.
11. 사용자 데이터 권한과 RLS를 항상 확인한다.
12. 모바일 앱 확장을 고려해 Supabase 중심 구조를 유지한다.
